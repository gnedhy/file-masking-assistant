# ADR 0004：本机还原记录明文备份

日期：2026-10-30。状态：已被 [ADR 0005](0005-企业单一部署与固定简短代号.md) 取代（本机模式与备份功能已删除）。

## 背景

还原记录只保存在当前浏览器的 IndexedDB 中。浏览器的持久保存只能防止磁盘紧张时的自动清理，防不了以下情况：
- 用户清除浏览器数据
- 换浏览器、换电脑
- 访问地址变化
- Safari 长时间不访问后的清理

而且是否批准由浏览器决定。原来的"持久保存"面板用户看不懂，保护范围也有限。

让任务跟随用户需要账号和服务端，这与"本机打一个来回"的定位不符，也增加了太多复杂度，因此不做。

## 决定

1. **自动申请，不再让用户操作**。首次保存任务时，静默申请一次持久保存，不关心结果。界面上只保留存储配额警告和一句备份提醒。
2. **提供导出和导入备份**。在本机任务抽屉里，把当前浏览器的全部任务导出为一个 JSON 文件，在其他浏览器或电脑上导入即可恢复。
3. **备份是明文，不设口令**。本机 AES 密钥不可导出（`extractable: false`），不设口令就无法生成可跨浏览器读取的密文。用户明确选择了不要口令。
4. **导入只新增**。已有的任务编号直接跳过，不覆盖本机版本。
5. **简短任务的编号永不共用**。导入前先占用标记：
   - 被同一任务占用（比如删除后再导入），可以继续。
   - 被其他任务占用，跳过该任务并提示冲突。
6. **无效备份整体拒绝**。只要有一个任务不合法，就什么都不导入。

## 后果与风险

- 备份文件含全部真实值，敏感程度等同原文件。因此导出前要确认，文件名带"含真实信息"，确认框提示不要交给 AI。
- 备份文件一旦外泄，等于这些任务的真实值全部外泄。这是用户接受的取舍。如果日后用于团队或企业场景，应重新评估是否需要口令。
- 还原钥匙文件仍然**不是**备份，这一点与 ADR 0003 一致。备份里包含钥匙文件的核验值，所以导入后原来的钥匙文件继续可用。
- 导入的任务会用目标浏览器的本机密钥重新加密。
- 不同浏览器的数据是各自独立的，ADR 0003 记录的"同名替身不等于来源认证"的边界依然存在。
- 操作记录新增 `backup_export` 和 `backup_import` 两种类型。服务端与前端共用同一张表，企业服务端需要重新部署才能接收这两种事件。
- 企业模式不显示备份区，也不走这条路径。
