# 2026-08-19 项目现状与验证基线

## 结论

当前版本已经超过纯视觉原型，属于可运行的浏览器功能验证版。核心格式引擎与失败关闭规则有自动化证据，但还不能宣称生产稳定或达到正式企业安全产品标准。

## 当前能力

| 流程 | 支持格式 | 当前边界 |
| --- | --- | --- |
| 制作脱敏文件 | XLSX、CSV | 用户确认字段后创建任务专属代号和本机映射 |
| 还原处理文件 | XLSX、CSV、DOCX、PPTX、安全静态 HTML | 只处理已声明文字区域，异常时停止输出 |
| 本机任务 | 当前浏览器 | 显示任务、映射数量和状态，可逐项删除 |

## 本次验证证据

- 自动化测试：45 项通过，覆盖 XLSX、XLSX 包预检、CSV、多样本往返、DOCX/PPTX、HTML 与站点打包。
- 生产构建：通过；构建产物可生成，但主应用包约 570 kB、ExcelJS 独立包约 940 kB，存在性能优化空间。
- 浏览器冒烟：制作/还原入口、深色模式、原理说明均可操作。
- 窄屏检查：390px 视口下页面宽度与视口一致，无横向溢出。
- 已知控制台问题：缺少 `favicon.ico`，产生一次 404，不影响核心流程。
- 外部完整验证集：现有桌面目录与测试脚本约定不一致，缺少测试映射文件，因此本轮未通过；这属于验证资产可复现性问题，不能记为功能失败，也不能记为验证通过。

## 安全与可靠性缺口

1. `npm audit` 报告 DOMPurify 直接依赖与 ExcelJS 间接 `uuid` 依赖存在中等级安全告警，需要升级、回归和审计门槛。
2. 本机映射密文与不可导出密钥同处浏览器存储，尚未完成威胁模型、密钥丢失、存储损坏、容量与浏览器清理场景验证。
3. 当前格式路由首先依赖扩展名，虽然 Office 包内部会再次验证，仍需统一“扩展名 + 内容签名”的预检结果与错误说明。
4. XLSX、DOCX、PPTX 与 HTML 的未承诺区域需要持续做残留代号和保真检查，避免范围描述超过证据。
5. 还缺少覆盖真实 AI 来源的长期兼容性矩阵；工程测试通过不等于完成 50 份文件、2–4 周业务试用目标。

## 可维护性缺口

- `App.jsx` 约 1,178 行，集中承载多阶段状态和多个抽屉；新增格式前应先建立端到端测试保护，再按用户流程拆分。
- `styles.css` 约 4,464 行，包含多轮追加规则；需要在不改变视觉基线的前提下整理组件样式和主题变量。
- 当前缺少统一的 `test` 命令和 GitHub CI，仓库无法自动阻止格式回归。

## 下一阶段原则

- 第一优先级是安全依赖、自动化验证和本机映射可靠性，不先扩展更多格式。
- 新格式必须完成“制作或还原入口 → 内容预检 → 任务匹配 → 失败关闭 → 原格式输出 → 自动化样本”的完整纵向闭环。
- DOCX/PPTX 脱敏输入属于后续候选；PDF、OCR、宏文件、嵌入对象和跨设备任务迁移继续保持范围外，除非另行完成产品与安全决策。
- 所有“稳定可用”结论都必须关联真实样本数量、AI 来源、试用周期和失败记录。
